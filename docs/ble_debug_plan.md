# 手机端与 ESP32 蓝牙联合调试与测试方案

本方案旨在指导如何安全、高效地进行 Android 手机端 (`phone_sorter`) 与 ESP32 分拣控制器 (`sorter_mini_controller`) 之间的低功耗蓝牙 (BLE) 双向通信联调，通过 PlatformIO 串口终端进行数据监控与验证。

---

## 1. 调试架构与数据流验证

联调的核心目标是确保以下双向数据链路的畅通：

```
                    ┌─────────────────────────┐
                    │    Android 手机测试端     │
                    └──────┬───────────▲──────┘
                           │           │
  (1) Target ID: 1-8       │           │ (3) STATUS: 0-3 / ERROR: 0-2
  (2) COMMAND: 0x01, 0x02  │           │     (Notify 特征订阅通知)
                           ▼           │
                    ┌──────────────────┴──────┐
                    │      ESP32 控制器        │
                    └──────┬──────────────────┘
                           │ 串口输出 (115200)
                           ▼
                    ┌─────────────────────────┐
                    │  PlatformIO 串口监视器   │
                    └─────────────────────────┘
```

---

## 2. 联调准备工作

### 2.1 从控端 (ESP32) 准备
1. 确保 ESP32 固件中 `BleManager.cpp` 的日志功能已启用，在接收到数据时能通过串口打印输出：
   - 目标特征写入回调 `TargetCallbacks` 需打印接收到的字节（`Target ID`）。
   - 指令特征写入回调 `CmdCallbacks` 需打印接收到的指令字节（`Command`）。
2. 将 ESP32 通过数据线连接至电脑，在 VSCode 中打开 `sorter_mini_controller` 项目。

### 2.2 主控端 (Android) 准备
1. 确保使用**物理 Android 手机**进行测试（低功耗蓝牙扫描与建链在 Android 模拟器上通常无法工作）。
2. 手机开启**蓝牙**与**定位服务**（低于 Android 12 的设备扫描 BLE 需要定位开启）。
3. 编译并安装打包好的最新版分级 App 到手机上。

---

## 3. 联调四步法 (逐步验证)

### 第一阶段：蓝牙建链与服务发现测试
*   **测试操作**:
    1. 在 VSCode 中启动 PlatformIO 串口终端，波特率设置为 `115200`：
       ```bash
       pio device monitor
       ```
    2. 给 ESP32 上电，观察串口输出。应能看到：
       `[BleManager] BLE Server starting...` 类似字样，表明蓝牙外设广播已就绪。
    3. 在手机上启动芦笋分级 App，授予相机与蓝牙权限。
    4. 观察手机 HUD 顶栏的状态提示。
*   **预期结果**:
    - **手机端**: 状态从 `🔴 蓝牙已断开` 自动跳转为 `🟡 正在连蓝牙...`，并在 3 秒内稳定在 `🟢 分拣机:待机`。
    - **ESP32 端 (串口)**: 打印出类似 `Client connected` 的连接成功日志，随后打印开启 Notify 描述符订阅的日志。

---

### 第二阶段：下行通道测试 (手机发送 ➔ ESP32 接收并打印)
*   **测试操作**:
    1. 保持串口监视器开启。
    2. **模拟分级下发**: 
       由于无需物理芦笋，我们可以使用一张打印有 ArUco 标记的纸张放置在摄像头前，或者点击屏幕进行一次手动/自动图像分析。
    3. 当算法识别成功并得出等级（如 Grade A）时，手机会自动触发写入 `TARGET` 特征。
    4. **模拟指令下发**:
       点击主界面菜单的复位或者通过触发故障唤出故障对话框，点击“一键复位 (Reset)”。
*   **预期结果**:
    - **ESP32 端 (串口)**:
      - 识别成功后，串口立即打印：`[BleManager] Target ID received: 1` (如果是 A 级) 或 `[BleManager] Target ID received: 8` (如果是 F 级)。
      - 点击复位后，串口立即打印：`[BleManager] Command received: 1`，同时状态机执行 `clearError()`，打印状态切换回 `HOMING` 流程。

---

### 第三阶段：上行通道测试 (ESP32 状态/故障 ➔ 手机 Notify)
*   **测试操作**:
    1. **状态切换同步**:
       断开 ESP32 电源重新上电，ESP32 自动进入 `HOMING` 归零流程。
       观察手机端 HUD 顶栏。
    2. **故障警报与弹窗**:
       在 ESP32 处于 `HOMING` 过程中，通过人工拉高限位开关模拟归零超时，或者在代码中人工注入一个错误使系统进入 `ERROR_STATE`。
       观察手机屏幕。
*   **预期结果**:
    - **状态同步**: 手机端 HUD 实时显示 `🟢 分拣机:归零中`，归零完毕后自动变为 `🟢 分拣机:分拣中` (或待机)。
    - **故障警报**: 手机屏幕立即弹出 `⚠️ 分拣机硬件故障警报` 红色警报对话框，准确显示 `归零超时 (Homing Timeout)`。

---

### 第四阶段：软恢复闭环测试 (全系统联合运行)
*   **测试操作**:
    1. 承接第三阶段的故障警报状态。
    2. 在手机弹出的故障警报对话框中，点击 **“一键复位 (Reset)”** 按钮。
    3. 观察手机界面与 ESP32 串口输出。
*   **预期结果**:
    - **手机端**: 故障弹窗消失，HUD 状态变为 `🟢 分拣机:归零中`。
    - **ESP32 端 (串口)**: 打印接收到指令 `0x01`，清空 ErrorCode，重新驱动 8 轴步进电机开启新一轮的安全归零，整个系统实现软恢复闭环。

---

## 4. 调试常见问题与排查表 (Troubleshooting)

| 现象 | 可能原因 | 排查步骤 |
| :--- | :--- | :--- |
| 手机一直显示 `🟡 正在连蓝牙...` | 1. 广播名称不匹配<br>2. 蓝牙权限未完全允许 | 1. 检查 ESP32 的 `BleManager.cpp` 广播名是否为 `"Sorter_Controller"`。<br>2. 检查手机系统设置，确保 App 拥有“附近设备”与“定位”权限。 |
| 串口没有打印数据 | 1. 波特率不匹配<br>2. 串口打印逻辑被注释 | 1. 检查串口终端波特率是否为 `115200`。<br>2. 检查 `sorter_mini_controller` 源码中的 `Logger.h` 级别是否限制了 `LOG_I` 输出。 |
| 写入目标 ID 后电机无动作 | 手机蓝牙写入成功，但 ESP32 队列溢出或未调用 FSM 调度 | 1. 检查串口是否正常打印了 `Target ID received`。<br>2. 检查 SorterFSM 的逻辑是否在 `RUNNING` 状态下正常从 `InputQueue` 中 pop 数据。 |
